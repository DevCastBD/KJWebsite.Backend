# Donor CRM (BE-060, #65)

## Who is a donor
A donor record is made (or refreshed) when a **non-anonymous** gift with an **email address** is confirmed, in the same commit as the confirmation and its receipt. Staff can also create a donor before any gift; it is listed with zero giving, no segments and an empty first-gift date.

Each donor has an id (`dnr_...`), a **stable donor key** carried by every receipt of that donor, and a unique lookup hash of the **current email** (`EmailKey`, case-insensitive). The stable key is fixed at creation: the keyed hash of the first email unless another donor already holds it, then a fresh key. Offline gifts can carry nullable `donations.DonorId`; it is required for student gifts. Non-anonymous online gifts now store the eligible signed-in donor's id, otherwise the id of the donor whose current `EmailKey` equals the keyed hash of the typed email at recording (#226, BE-112). A first-time email stores no id; the donor is still created at confirmation. Confirmation finds a stored donor id and uses that donor's stable key for the receipt. Existing donors were migrated with the lookup hash equal to their key.

`POST /api/v1/donations` still allows anonymous callers, remains idempotent and has the same request and response. A valid donor access token takes precedence over the typed email: it must have role `Donor`, the password must already be changed, and the donor must be active with sign-in not disabled. A missing, expired, revoked or non-donor token never refuses the gift; an ineligible caller falls back to the email rule. Recurring plans store the same nullable `DonorId` on `recurring_plans`, with no backfill; later instalments will inherit it, but instalment creation is not built yet.

Staff can correct a donor's email unless the donor has a sign-in account (`409 EMAIL_HAS_ACCOUNT`). History stays attached through the stable key; no stored receipt is edited. Confirmed gifts could never move because receipts freeze the donor key and are append-only. Storing the donor id at recording closes the pending-gift gap: an email change before confirmation, or another donor later taking the old address, never moves a gift recorded with an id. Gifts without an id still match by current email at confirmation. Old rows remain unchanged with a null donor id and keep their receipt's donor key, so confirmed gifts stay attached to the same donor. There is no backfill or mapping table. No email history table is needed: Finance already audits changes to the donor's email key and protected email, and the stored donor id preserves attribution.

With an offline gift's `donorId`, the donor's own current name, email, phone and language are used at recording; typed contact details are ignored, including malformed email. Online gifts retain the typed contact details. For offline gifts with `donorId`, the receipt snapshot and receipt notification use the donor's current name and email at approval; online gifts keep the typed name and email for the receipt snapshot and notification recipient. Contact details still follow the latest gift whose email is the donor's current email, whether or not it carries the donor id. A gift tied by id whose typed email differs from the donor's current email (a signed-in donor typing another address, or an old copy confirmed after an email change) never rewrites the donor; staff correct contact details through the donor profile (#211). The stable key never changes; reversal rows still copy `donorId`.
Thank-you and update messages are sent, subject to consent, to the donor's profile address, so when a signed-in donor types a different email address on the form, the receipt uses the typed name and email and is sent to the typed address, while thank-you and update messages go to the profile address.

**An anonymous gift creates and touches nothing**, and a walk-in with no email has no record: an anonymous option that still left a profile would not be anonymous. Anonymous gifts store no donor id and still match by email at confirmation; a known donor's email gives the receipt that donor's key and the gift appears only in that donor's statement. Contact details are encrypted. Offline gifts, reversals and all read paths (donor list and history, statements, reports and reconciliation) are unchanged; reads still join on the receipt's donor key.

## Giving history and lifetime value
Nothing about totals is stored on the donor, so nothing can drift from the books. Gift count, first and last gift dates, lifetime totals, segments, the donor list row, export and message segments, and donor-facing history are **derived from valid, non-anonymous receipts** (a reversed gift's receipt is void and drops out), per currency (never converted), with money and in-kind value kept apart. The staff gift list also shows reversed gifts as `refunded` without counting them. `GET /api/v1/admin/finance/donors/reconciliation` proves it: for every donor and currency it compares the receipts' total with the net donation income (`4010`/`4020`, reversals netted) the ledger holds for the same donations, and reports `reconciled` plus any difference.

`GET /api/v1/admin/finance/donors/{id}/donations` and the `gifts` array of `GET /api/v1/admin/finance/donors/{id}` (`finance.view`) list non-anonymous gifts newest first, including reversed gifts with `status` `refunded`; every other gift has `status` `confirmed`. A gift is reversed when a reversal donation exists for it, the same rule used by `GET /api/v1/admin/finance/donations`. Its original receipt number, amount, date and designation stay unchanged. A donor whose only gift was reversed shows one `refunded` row with a zero gift count and total. Donor-facing endpoints (#212), including `GET /api/v1/donors/me/donations` and its totals, still omit reversed gifts.

## Profiles and sign-in (BE-104, #211)
- **Profile**: type is `individual` or `organisation`; an organisation needs its name (max 200). Name is required (max 200), email is required and valid (max 254), phone is optional (`+` followed by 7 to 15 digits), language is `bn` or `en` (default `bn`). Address (max 500) and internal notes (max 2000) are encrypted; country is two uppercase letters. Donor status is `active` or `inactive`. The row also holds `accountSubject`, `accountShared`, `accountStatus` (`none`, `active`, `disabled`) and `version`.
- **Read** (`finance.view`): the list accepts `status`, `accountStatus` and `hasAccount=true|false`; unknown values return `400 VALIDATION_ERROR`. Rows include type, status and account status. Detail returns a `profile` object and an `ETag`; `mustChangePassword` is read live from Identity and is `null` without an account or when Identity cannot be reached.
- **Create and edit** (`finance.donor.manage`): `POST .../donors` returns `201` with an `ETag`; invalid fields return `400 VALIDATION_ERROR`, and an existing email in any letter case returns `409 DONOR_EXISTS` naming the existing donor id. `PATCH .../donors/{id}` requires `If-Match` with the quoted version number: missing gives `428 PRECONDITION_REQUIRED`, stale gives `412 PRECONDITION_FAILED`. Omitted fields stay; an optional text field sent as `""` is cleared. Every change increases the version, including a gift refreshing contact details.
- **Provision sign-in** (`finance.donor.provision`): `POST .../donors/{id}/login {password}` calls Identity (#210) with the staff member's own token and uses the donor email as the sign-in name. It returns `201` with `{donorId, accountStatus, accountShared, mustChangePassword}`, or `200` when it adds the Donor role to an existing member account (`accountShared=true`). Errors are `409 ACCOUNT_EXISTS`, `409 EMAIL_TAKEN` (an account of another kind), `409 DONOR_INACTIVE`, `400 VALIDATION_ERROR` (password policy) and `503 AUTH_UNAVAILABLE` (nothing saved). The password is never returned, logged or audited.
- **Manage sign-in** (`finance.donor.provision`): `PUT .../donors/{id}/login/password {password}` sets a new initial password, requires a change and ends sessions; it rejects `409 NO_ACCOUNT` and `409 ACCOUNT_SHARED`. `PUT .../donors/{id}/login/status {status: active|disabled}` disables or enables sign-in; disabling ends sessions. It rejects `409 ACCOUNT_SHARED`, `409 NO_ACCOUNT` and, when enabling for an inactive donor, `409 DONOR_INACTIVE`.
- **Inactive donors**: setting donor status to `inactive` disables a donor-only sign-in in Identity first; failure returns `503 AUTH_UNAVAILABLE` and saves nothing. A sign-in shared with a member is left alone. Reactivating a donor does not enable sign-in.
- **Identity lookup**: `GET /api/v1/admin/auth/donors/{userId}` (`finance.view`) returns status, `mustChangePassword`, roles and `shared`; an account without the Donor role returns `404`.
- **Audit and links**: changes are audited with before and after values, excluding name, email, phone, address, notes and both keys. `linkedStudents` and the Finance has-active-links filter are not built yet; they wait on a Finance-to-Sponsorship call. Student-donor links are built in Sponsorship (#214).

## Donor self-service (BE-105, #212)

- **Endpoints:** `GET /api/v1/donors/me` and `GET /api/v1/donors/me/donations` are read-only, served by Finance and routed by the gateway.
- **Access:** Policy `kj.donor` requires the `Donor` role claim. The role holds no permission key. Other roles, including back-office and member tokens, receive `403`; no token receives `401`. Accounts awaiting an initial password change receive `403 PASSWORD_CHANGE_REQUIRED`.
- **Ownership:** The token subject matches the donor's account subject. Neither endpoint accepts a donor id; donor ids in query parameters or request bodies are never read. A `Donor` token without a donor row receives `404 NOT_A_DONOR`.
- **State:** Every request checks the session with Identity before donor and account state. Disabling through Finance (`PUT /api/v1/admin/finance/donors/{id}/login/status`) or directly in Identity makes the old token return `401 UNAUTHORIZED` on every donor route; sign-in returns `403 ACCOUNT_DISABLED`. A shared member and donor sign-in disabled through membership is also ended by the session check, even though Finance holds only the account state it last set. Inactive donors receive `403 DONOR_INACTIVE`; Finance retains `403 ACCOUNT_DISABLED` as a second line when the session check is switched off. If Identity cannot answer, authenticated calls fail closed with `503 AUTH_UNAVAILABLE`.
- **Profile:** Returns `name`, `type`, `organisation`, `email`, `phone`, `address`, `country`, `language` and `since` (the donor record's creation date). Missing optional values are empty strings. Never returns notes, staff status, account state, keys or version.
- **Donations:** Returns `{ items, total, limit, offset, totals }`. Items contain only the donor's own gifts from valid, non-anonymous receipts, matched by the donor's stable key. Gifts from receipts voided by a reversal are excluded. Order is newest first by receipt date, then receipt number.
- **Item fields:** `id` (donation id), `reference`, `date`, `amount` (two decimals), `currency`, `designation`, `designationType`, `designationId`, `studentName` (nullable), `status` (`confirmed`), `inKind` and `receiptNumber`. `designation` is the campaign title in the donor's language when set, otherwise `General` for general giving, otherwise the designation id. For student gifts, Finance asks Sponsorship once per page, only when the page has student gifts, with the donor's own token. Visible students have `studentName` set to the permitted live or frozen preferred name and `designation` set to `Student sponsorship: {name}` (`শিক্ষার্থী পৃষ্ঠপোষকতা: {name}` for a `bn` donor); otherwise `studentName` is null and the label is plain `Student sponsorship` / `শিক্ষার্থী পৃষ্ঠপোষকতা`. `designationId` stays null for student gifts; other gifts have `studentName` null. If Sponsorship is unreachable, the response is still `200` with null names and plain student labels. Student visibility and links are documented in [SPONSORSHIP.md](SPONSORSHIP.md). No receipt download link is returned.
- **Paging and filters:** `limit` is `1` to `100` (default `20`); `offset` is `0` or more. Optional `year` filters the receipt date's calendar year, from `1970` to `9999`. Out-of-range values return `400 VALIDATION_ERROR`.
- **Totals:** `totals` contains `{ currency, cash, inKind }` entries over all gifts matching the filter, independent of paging. Currencies are never added together.
- **Methods:** `POST`, `PUT`, `PATCH` and `DELETE` on both paths return `405 METHOD_NOT_ALLOWED` with `Allow: GET` and change nothing.
- **Caching:** Every response, including refusals, carries `Cache-Control: private, no-store` and `Vary: Authorization`.
- **Internal identity:** `GET /api/v1/donors/me/identity` returns `{ id, language }` with the same checks as `/me`; it is internal, not routed by the gateway or listed in `openapi.v1.yaml`, and is used by Sponsorship with the donor token.
- **Out of scope:** `/donors/me/statements`, `/recurring` and receipt download. Sponsorship serves `/donors/me/students` and photos; see [SPONSORSHIP.md](SPONSORSHIP.md).

## Segments (reproducible)
Pure functions of a donor's gifts, an `asOf` date and configuration (`Finance:Donors`): nothing reads "now" or a stored flag, so any segment can be re-run for any past date. Gifts after `asOf` do not exist yet.
- **new**: first gift within `NewWithinDays` (90) of `asOf`
- **lapsed**: last gift more than `LapsedAfterMonths` (12) calendar months before `asOf`
- **major**: lifetime giving in any one currency at or above its `MajorThresholds` entry (BDT 100000, USD 1000, GBP 800, EUR 900); currencies are never added together
- **recurring**: any gift came from a recurring plan

## Communication consent
Three purposes, **opt-in only**: `thanks` (follow-up thank-yous beyond the receipt), `updates` (impact news), `appeals` (fundraising asks). Nothing is assumed from silence.
- Every grant and withdrawal is a new append-only row (`donor_consents`); the latest per purpose is current. Consent here is separate from newsletter consent (#80): a donation is not a subscription.
- The donation form (public, and offline entry) may carry an optional `communicationConsent`; ticked, it grants `thanks` and `updates` (source `donation_form`) and **never `appeals`**. Staff can record a change with `POST .../donors/{id}/consent` (source `admin` or `donor_request`; `finance.donor.manage`).
- **One gate** (`DonorMessenger`) decides every non-receipt message. If the donor's latest word for the message's purpose is not a grant, the message is **not queued** and a suppression row (`donor_suppressions`, append-only) records it, so it is provable nothing went out without consent. Receipts are transactional and are not gated.

- **Student-link notices:** `GET /api/v1/admin/finance/donors/{id}/link-target` and `POST .../donors/{id}/link-notices { linkId }` require `sponsorship.link.manage`; the POST requires the `Idempotency-Key` header (`400 VALIDATION_ERROR` without it) and returns `queued|suppressed`. Template `donor.student_linked` maps to `updates` consent and holds only the link id. Bilingual templates do not exist yet; delivery waits on the email sender.

## Thank-you automation
At confirmation, a thank-you is queued to the outbox (`donor.welcome_thanks` for the first gift, `donor.thank_you` after) only if the donor holds `thanks`; otherwise it is suppressed and recorded. Delivery waits on the email sender (BE-032/033).

## Messaging a segment
`POST .../donors/messages {template: donor.appeal|donor.update, segment?, asOf?}` (`finance.donor.manage`) queues the template to the segment through the same gate (appeals need `appeals`, updates need `updates`) and answers how many were queued and suppressed.

## Export
`GET .../donors/export?segment&asOf&consent` (`finance.donor.export`, Admin and SuperAdmin only) returns CSV for the same donors and rules as the list, so an export for a date can be reproduced byte for byte. `consent=appeals` (or thanks, updates) keeps only donors who granted it. Cells that a spreadsheet could run as formulas are neutralised, and **every export is logged** (`donor_exports`: who, segment, date, filter, rows).

## Retention
How long donor records are kept waits on the retention decision (#110); financial records (receipts, ledger) are kept regardless. The donor row is the only mutable table here; consent, suppressions and the export log are append-only.
